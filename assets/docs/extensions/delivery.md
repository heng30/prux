# delivery（把回合的改动交付出去，并盯到 PR 变绿）

`delivery` 扩展把「改完了」变成「交付完了」：在 agent 结算前自动建分支、提交、推送、开 PR，
然后等 CI 与评审出结论；红掉的检查与要求修改的评审意见会被整理成一条**失败报告**喂回模型并
**续跑一轮**，模型修完再结算时又会重新提交、重新推、重新看——直到全绿、用满次数、或同一条失败
反复出现。

- 扩展名：`delivery`（`settings.json` 的 `enabledExtensions` / `/extension` 面板切换）
- **默认关闭**：只在 `Dev` 模式注册。它会写 git 历史并推远端，只能由你显式打开。
- 不提供任何模型可见的工具：交付发生在结算边界上，对工具列表和系统提示没有影响。
- **永远不会 merge**：`stage` 最高只到开 PR。

## 交付流程

一次结算（主 agent 结束一轮、且用户没有排队输入、也没有被中断）时：

1. 确认工作目录在 git 仓库里；不是仓库就静默跳过。
2. 量本回合有没有改动（`requireEdits` 只在本回合调用过 `edit` / `write` / `bash` /
   `powershell` 时才继续；`/delivery run` 不受此限制）。
3. 若当前就在基线分支上，就新建一条 `prux/<日期>-<时分>` 分支再干活，不动基线分支。
   「基线」的判定顺序：配置里的 `base` → `origin/HEAD` 指向的分支 → 约定俗成的名字
   （`main` / `master` / `trunk`，给没有远端的新仓库兜底）。
4. `git add -A` + `git commit`，提交信息是 `prux: <本会话第一条需求的单行摘要>`。
5. `stage` 允许时 `git push -u origin <分支>`。
6. `stage` 到 `pr` 时：确认 `gh` 已登录 → 确定目标分支（`base`，留空则由 `gh` 探测仓库默认
   分支）→ 已有 PR 就复用，没有就 `gh pr create`（`draft` 控制是否草稿）。
7. 轮询 PR 状态，直到全绿 / 有阻塞 / 超时（见 [CI 修复循环](#ci-修复循环怎么收敛)）。

## 停在哪一步（stage）

| 值 | 动作 | 适用场景 |
|----|------|----------|
| `branch` | 只提交到会话分支，不碰远端 | 想自己看一眼再决定推不推 |
| `push` | 提交 + 推 `origin`，不开 PR | 远端已有自己的评审流程 |
| `pr` | 提交 + 推 + 开 PR + 跟 CI 与评审（缺省） | 常规 |

`/delivery stage push` 等命令直接改配置，立即生效。

## 配置

`agent_dir()/extensions/delivery.json`（全局唯一，没有项目级配置——能提交进仓库的配置不该
有权改你的推送目标）：

```json
{
  "stage": "pr",
  "maxIterations": 2,
  "timeoutSecs": 900,
  "pollSecs": 20,
  "base": "",
  "draft": false,
  "requireEdits": true
}
```

| 键 | 缺省 | 含义 |
|----|------|------|
| `stage` | `"pr"` | 停在哪一步：`branch` / `push` / `pr` |
| `maxIterations` | `2` | CI 或评审不过时，最多把失败喂回模型几次。`0` = 只交付一次、不跟 CI |
| `timeoutSecs` | `900` | 每次结算等 CI 出结论的总时限；超时按「还在跑」收手，不喂回模型 |
| `pollSecs` | `20` | 轮询间隔。推完先等满一个周期再读状态，否则可能读到上一次推送的结论 |
| `base` | `""` | PR 目标分支；留空用 `gh repo view` 的默认分支 |
| `draft` | `false` | 开 PR 时是否用 draft |
| `requireEdits` | `true` | 只在本回合调用过写类工具时才交付（纯问答轮不交付） |

缺键会自动回填；文件写坏了不会被覆盖，配置退回缺省值并在聊天区提示一次。

## 命令

| 命令 | 作用 |
|------|------|
| `/delivery`（或 `/delivery status`） | 打印当前配置、本会话的分支 / PR 号、本回合已喂回几次、最近一次交付的结论 |
| `/delivery run` | 立刻交付一次：忽略 `requireEdits` 与「回合开始前就脏」的限制 |
| `/delivery stage branch\|push\|pr` | 改停止点并写盘 |
| `/delivery reset` | 清掉本回合的续跑计数与失败指纹（不改分支、不改 PR） |

`/delivery run` 在后台线程执行（等 CI 可能是分钟级），结果回聊天区，不阻塞界面。

## CI 修复循环怎么收敛

三条独立的收敛条件，缺一条就会无限烧钱：

| 条件 | 行为 |
|------|------|
| 用满 `maxIterations` | 停止续跑，提示「PR 仍不绿」，交回你自己决定 |
| 失败报告与上次完全相同 | 停止续跑（同一条错误再喂一次也不会有新结果） |
| 等满 `timeoutSecs` 也没出结论 | 停止等待，报「还有 N 个检查 pending」，不喂回模型 |

喂回模型的是结构化清单，不是原始日志：失败的检查（`名称 — 结论`）与要求修改的评审
（`作者: 正文`），外加 PR 链接。模型据此改代码，下一次结算会重新走完整条交付流程。

## 三条不越的线

- **不替你合并**：`stage` 最远到 `pr`。合入看的是人。
- **不吞掉回合开始前就脏的工作区**：那份改动不是本回合的产物，默认拒绝交付并说明原因
  （`/delivery run` 是显式例外）。否则 `git add -A` 会把你的临时改动卷进 `prux:` 提交里。
- **不猜远端**：`origin` 不存在、`gh` 没登录、探测不出默认分支，一律停下报原因，不做兜底推送。

## 和 vet 的分工

- `vet` 管**本机**：结算前跑测试 / lint / 类型检查，红了就喂回去继续修。
- `delivery` 管**交付**：本地过了不等于 CI 会过，它负责把改动推上远端并把**远端**的结论喂回来。
- 两个都开时，一轮里 `vet` 先要求你绿，`delivery` 再把结果交出去；两者的续跑计数彼此独立。
- 子代理的结算不触发交付，也不触发 vet：交付的对象是主 agent 这一轮的成果。
